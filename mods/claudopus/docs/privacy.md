# What Claudopus does on your Mac

On Linux it does the same, except as [On Linux](guide.md#on-linux) says: keys and passwords are files only you can read under `~/.local/share/claudopus/keyring`, and it runs `uname`, `hostname`, `xdg-open`, `notify-send` and ImageMagick where a Mac runs its own tools.

Where its data lives, what it sends, and every hook, tool and program it runs, for you and for the plugin directory's reviewers. The short version is under [Privacy](../README.md#privacy) in the README.

## In short

- **What it saves.** Claudopus saves the files listed under [Memory](guide.md#memory) in `~/.claude/claudopus` on your own machine. Delete the folder and they're gone. Keys you type in its boxes are saved in this Mac's keychain instead, and stay there until you remove them. Claudopus never saves an admin password.
- **What it sends.** Claudopus sends data only to Claude, through Claude Code: the texts it adds to prompts (its rules, your topics, notes on each topic, and results not yet passed on), and after each reply one short call with the start of your message and of the reply, to title the chat and note what was asked and done. With `macs` set, it also sends to those Macs only, over your own SSH. It reads their open chats and their tasks, hands them this Mac's chats without the commands and texts its tasks run or send, and copies results each Mac lacks to it, marks included. Every hour, or as Config's Look for new versions says, it reads `https://www.claudopus.ai/version.json`, which holds the current version number, git's fingerprint of Claudopus's folder as released, its size and the first line of each recent version's changes, When that is newer than yours, a small box in the panel's header says so. Claudopus fetches the release's tag from this marketplace's origin on GitHub with `git fetch` only when you press Download, and Claude Code updates Claudopus from it only when you press Install. Claudopus never installs by itself and doesn't reload a chat: the header says the new version is ready and to type `/reload-plugins`. Only if you join the leaderboard from its Leaderboard tab, it sends the leaderboard on claudopus.ai (a Supabase database) your username, whether your stats are public, and sums for today, the last 7 days, the last 30 days and all time: time of work, time on the clock, tokens by kind and by model, API cost, tasks, messages, to-dos and workflows done, and, only while your stats are public, when each task ran and on which model, for a timeline with no task names. Never a title, a path, a file or anything you or Claude wrote. It sends them as you join, then every 3 minutes from one chat while Claude Code is open. Joining gives Claudopus a secret, kept in `~/.claude/claudopus/leaderboard.json`, that sends your figures and takes them off; Leave removes your row at once. There is no telemetry and there are no other network calls of its own.
- **Keys and passwords.** What you type in its key boxes stays in this Mac's keychain. Claudopus uses it only for the commands Claude runs, on this Mac or over SSH to the host named. [What you see](guide.md#what-you-see) says what that allows and where the hiding stops. A box's words are the panel's own, never text from the request. Claudopus refuses commands from Claude that write into the boxes folder or read the boxes' keychain entries. That catches mistakes and common tricks, but it can't stop code set on getting around it.
- **Admin commands.** Claude runs a command as administrator only after you press Allow on the task's card, which shows the exact command and the Mac, unless you set Config never to ask. Claudopus saves no admin password. Each command asks for it, in macOS's own box on this Mac's screen, or elsewhere in the panel's box, locked to that one command and dropped after it.

Everything stays on your machine, apart from what Claude Code itself sends to Claude.

## What it sends, and where

Only if you join the leaderboard from its Leaderboard tab, it sends the leaderboard on claudopus.ai (a Supabase database) your username, whether your stats are public, and sums for today, the last 7 days, the last 30 days and all time: time of work, time on the clock, tokens by kind and by model, API cost, tasks, messages, to-dos and workflows done, and, only while your stats are public, when each task ran and on which model, for a timeline with no task names. Never a title, a path, a file or anything you or Claude wrote. It sends them as you join, then every 3 minutes from one chat while Claude Code is open. Joining gives Claudopus a secret, kept in `~/.claude/claudopus/leaderboard.json`, that sends your figures and takes them off; Leave removes your row at once.

After each reply, one short call through Claude Code (`$.model.complete`, Sonnet) sends the start of your message and of the reply to Claude, to title the chat and note what was asked and done. It sets that title, and reads the chat's own id, through the Claude desktop app's built-in session server (`ccd_session_mgmt`: `get_session`, `set_session_title`). With Macs named under `macs`, it runs `ssh` to each (key login only, never asking for a password): every 10 seconds one chat on this Mac reads the files under `~/.claude/claudopus/live` there that changed in the last three minutes, leaves there this Mac's own such files (`live/pushed/`), and brings back the answers pressed there for this Mac's chats (`live/outbox/`); every two seconds one chat takes from there the names pressed for this Mac to open (`live/outbox/<this Mac>/o-*.json`), over one connection held open a minute after its last use (`ControlMaster`, its socket in `/tmp`); an answer you press for one of their chats is written into that Mac's `live/answers`. At most every two minutes one chat reads the `meta.json` of each result under `~/.claude/claudopus/reports` there, brings over with `tar` the result folders this Mac lacks and hands that Mac those it lacks (each put in place whole, only where no folder has its name, with its home path in `meta.json` and `report.md` changed to the other Mac's), and writes a result's `meta.json` on either Mac only to carry over an archive, a bring back or an answer, there only when it is unchanged since it was read. Each chat reads its own entry in `~/.claude/sessions` every 20 seconds for its Remote Control and app ids, which a press on its name in another panel opens; and, while another Mac's chats are listed, the Claude app's own session files in `~/Library/Application Support/Claude/claude-code-sessions`, listed at most every 30 seconds and each read once, for only its app id and chat id, to know which of those chats this Mac's app holds. Unless `updates` is `false`, one chat looks at the version page, at most as often as `updateEvery` says (every hour as shipped; Config's Check now looks at once and does nothing more): it fetches `https://www.claudopus.ai/version.json` (`$.http.fetch`, a plain GET with nothing of yours in it) and saves what it saw in `~/.claude/claudopus/update-seen.json`; a look downloads and runs nothing. When the page names a newer version, a press of Download in the panel's header runs `git fetch` of that release's tag only (`v<version>`, from `origin`, GitHub for most, with `GIT_TERMINAL_PROMPT=0`) into the ref `refs/claudopus/update` of the marketplace's own git clone that Claude Code keeps (or of the git of a folder of the code that is Claudopus's checkout), then checks with `git rev-parse` and `git merge-base` that Claudopus's folder in it is the very tree the page named, or deletes the ref (`git update-ref -d`). A press of Install reads the page and checks the download again, then runs Claude Code's own `plugin marketplace update` and `plugin update` for Claudopus (the engine the chat runs on, `$CLAUDE_CODE_EXECPATH`, else `claude`) and checks the installed copy against the page's fingerprint; for a folder of the code it runs `git merge --ff-only` instead, which git refuses before changing anything when your own work would be lost. Claudopus saves the steps' state in `~/.claude/claudopus/update-steps.json` and what Not now put off in `update-later.json`. A lock file, `update.lock`, keeps two chats from doing a step at once. Claudopus never runs `/reload-plugins`: the header says the new version is ready and to type it. In a chat run from another Mac, it saves `~/.claude/claudopus/reloads/<chat>.json`, naming the installed version, so copies left running by a reload typed there wait. No telemetry, no other network calls.

## What it puts in prompts

Into every chat: the working principles (`rules/CLAUDE.md`, or your copy in place of it), as one more instruction file. With your first message in a chat, after a compaction and when the text changes: the chat's rules (`roles/chat.md`), the list of your topics with the path of each topic's notes, how full each running task is, and the results not yet passed on. Into each agent the chat starts, after its instructions: the task rules (`roles/work.md`), the path of the chat's saved words and the panel's to-do rule. Into a compaction: a line asking it to keep what you asked for and the tasks under way. Into a running agent's chat: your message about the task, or your answer from the panel, and a short reminder when it has gone many steps without updating its card. A message over 12,000 characters is sent as its start, its end and the path where it was kept.

## The prompts it submits

Claudopus submits a prompt to the chat when you press an answer to what a saved result is waiting on, and when you press the welcome's button to index your past chats. A question from Claude, and an answer on a card, never go in as a prompt. Claudopus shows a question in the chat as its own notice, with a row only the chat's Claude reads. If you answer a card whose task has already ended, Claudopus sends that task a message saying what you pressed and what it answers, and the task starts again from it.

## What its hooks do

- `prompt.submit`, `prompt.context`, `session.compact`, `agent.spawn`: add the texts above. `agent.spawn` adds only to the prompt of an agent the chat itself starts; it changes no permission mode, model or tools.
- `tool.call` (every tool): in a chat's own thread, while background tasks are on, it lets through only the tools that start and talk to agents and workflows (`Agent`, `Workflow`, `SendMessage`, `ListAgents`, `TaskStop`, `ToolSearch`, `AskUserQuestion`, `SendUserFile`, `ReadNotifications`, `Skill`, Claudopus's own tools, the app's `mcp__ccd_` tools) and the three that read (`Read`, `Grep`, `Glob`), so the chat reads files in its own thread to answer a question a few files answer, and refuses the rest, everything that changes a file or runs a command, with a line saying to start a task for it. An `Agent` call from the chat that copies the chat (`fork`) or names no model is refused the same way, and so is an `Agent` call from the chat or from a task that names an older model or Haiku. A `Bash` command in one of the usual forms that read a password from the keychain is refused everywhere. It catches mistakes, but it isn't a wall. A `Bash` command that runs `bin/admin` is held until you press Allow once, Always allow this command or Deny on its task's card (Config can make that once per task, or never). The press is held only in the hook's memory, and what it allows is left for `bin/admin` as a sealed file in `~/.claude/claudopus/admin-grants`, taken once. A call that reads or writes that folder, `admin-allowed.json` or the keychain entry that seals them (`claudopus-admin-gate`) is refused, and so is one that reads the saved admin passwords (`claudopus-admin`), typed, quoted apart or in a script it runs. A call refused in a chat's own thread is never held and leaves no grant. A `Bash` command that runs `bin/release` is held the same way until you press Release on its task's card, and what it allows is left as a sealed grant for that worktree and branch, which `bin/release` takes once. A `Write`, `Edit` or `NotebookEdit` of `config.json`, `rules/`, `roles/` or a repo's `.git/release.local` is held until you press Allow on its card; a `Bash` command that writes those, or anything that writes `live/` or the update's own files, is refused. What `config.json`, `rules/CLAUDE.md`, `roles/chat.md`, `roles/work.md` and `admin-allowed.json` last held as Claudopus or your press set them is saved in `~/.claude/claudopus/admin-known.json`, sealed with a key of its own beside the gate's (account `known`), which Claude never reads or writes; the hook reads the saved text in place of a file that differs, and compares the files with it as Claudopus loads, as you send a message, as every call begins and as each `Bash` call ends: one that differs is put back (`rm`, then the hook writes it), what it held is saved beside it as `<file>.<time>.put-back`, and the change is shown on a card for Allow or Deny. A saved copy missing or not sealed right where its key exists counts for nothing: own files move aside to `.put-back` copies and are offered. These guards and the one on the gate's own files read the scripts a command runs too, and a command that runs one of Claudopus's runners with another `HOME` or `XDG_DATA_HOME`, or without `CLAUDECODE`, is refused; the runners themselves take the home folder from the user database (`getpwuid`), never `HOME`, and never read `XDG_DATA_HOME`. Once you have saved a key, what any other tool returns has every saved value replaced by its name. Agents' calls are otherwise passed on unchanged; the hook counts their steps for the cards.
- `tool.call` on `Workflow`: passed on unchanged. A workflow it started is followed on a card.
- `tool.call` on Claudopus's own tools (`mcp__claudopus__note`, `todo`, `ask`, `update`, `recall`): answers them itself; it stands in for no other tool.
- `tool.check` and `classic.PermissionRequest`: read which call the app is about to put to you as a prompt, to show it in the panels; the verdict and the request are passed on unchanged, and the mod never answers a prompt: an answer to one left in a file, by another panel or another Mac, is dropped.
- `tool.describe`: rarely used tools (`ReportFindings`, `SuggestPluginInstall`, `SuggestSkills`, `SearchPlugins`, `ScheduleWakeup`, `Workflow`, and the browser, iOS simulator and visualize servers) wait behind ToolSearch instead of loading into every chat.
- `turn.step`: when you pick another model for a task in its card, its next steps ask for that model. A step of a task or a helper that the app sends to Haiku asks for Sonnet 5.5, or the model you picked, instead, and one the app sends to another older model is left on it, with its card saying so; the request and response are otherwise untouched, and only the token count and model name are read.
- `turn.complete`, `session.measure`, `session.start`, `command.run` (`/claudopus`, `/servers`), `ui.render`: keep the cards, the bar above the prompt and the panel's tabs.
- From any of them it may show a notification through the app (`$.ui.notify`), play its own `sounds/ready.wav` (for what needs you, only where the notification could not carry its own sound), or put text you pressed Copy on onto the clipboard (`$.ui.copy`).

## Tools it runs itself

`TaskStop`, when you press Stop on a card or a workflow.

## Programs it runs, and why

Each by name with its arguments in the call: `lsof` and `ps` to list servers for `/servers`, and `ps` as a command waits on your OK and every two seconds after, to see that it started; `kill` when you stop one there; `jq` (looked for in `/usr/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, then the path) and `du` for Stats; `head` and `tail` to read the ends of a task's record; `sips` for thumbnails; `mkdir`, `cp` and `find` to copy a result's pictures into its folder and drop old thumbnails; `mv` to set aside your copy of a text on Reset and to put an answer for another chat in place whole; `rm` to remove a chat's own file in `live/` as it closes and the answers it has read; `scutil --get LocalHostName` for this Mac's name on the other Macs; `ssh` to the Macs named under `macs`, with `sh`, `date`, `find`, `tr`, `mkdir`, `cat`, `mv`, `rm` and `basename` run there to read their chats' files, leave this Mac's, and leave and collect answers, and `tar` and `cksum` there and here to copy results each Mac lacks and to write a result's marks only when unchanged; `open` (or `xdg-open`) to show the memory folder, a picture or a text in your editor, and to open another chat in the Claude app (`claude://code/` with its Remote Control id, or `claude://code/continue?session=` with the app's id for a chat this Mac's app holds, here or run on another Mac over SSH); `grep` to search the memory for `recall`; its own `bin/secret` with `--list` and `--hide` to hide saved keys; in a chat run from another Mac, `security -i` with what you type in a password or key box on its stdin, `security find-generic-password` without `-w` to see it was saved and `delete-generic-password` for one whose runner stopped, `sh -c 'set -C'` for the mark that tells one chat to name the box, and `rm` for a box cancelled or stale; for the admin commands you allow, `sh` running `security`, `openssl` and `perl` to seal what you allowed with the gate's key in this Mac's keychain (made at your first Allow, made anew when you take something back), `sleep` for the second between checks of what you pressed while a command is held, `find` and `rm` to clear grants nothing took, and `security delete-generic-password`, run once in a shell as Claudopus loads, to remove an admin password an earlier version saved; `git` (`fetch` of the release's tag from `origin`, `rev-parse`, `merge-base`, `update-ref -d` and, for a folder of the code, `merge --ff-only`) when you press Download or Install; Claude Code itself (`plugin marketplace update <marketplace>`, then `plugin update claudopus@<marketplace>`) to update Claudopus when you press Install, with `sh` making the lock file (`update.lock`) that keeps two chats from doing a step at once and `rm` removing it; and its own `bin/notify` with the notification's title, text and what a click opens (`claude://code/continue?session=` with this chat's id in the Claude app, else the app it runs in), which starts `notifier/Claudopus.app`, or for what needs you `--asks` (and `--chime` unless `sound` is off) to start `notifier/ClaudopusAsks.app` with its sound first, then `osascript` if none may notify.

## What it does not run by itself

`bin/release` is a shell script the task rules point agents to for putting a task's changes on a repo's main. It releases only with a grant your press on the task's card left for that worktree and branch, under two minutes old, locked as `bin/admin`'s are, and takes it once; it reads main's committed `.release` and this Mac's `release.local` in a shell of its own as values only, never a branch's `.release`. It runs `git` (fetch, a checkout of its own in a temporary folder, merge, commit, push, tag), `gh` to make the version's GitHub release when the repo's `.release` asks for it, the build and checks the repo's `.release` names, keeps a lock folder under `~/.claude/claudopus/locks` while it runs, and puts a `pre-push` hook in a repo that has none, which refuses a push of main from inside Claude Code only. `bin/admin` and `bin/secret` are shell scripts the task rules point agents to: an agent runs one with Bash when a step needs an admin command or a key, and it leaves a request naming what it needs (in fields the panel words itself: the kind, the Mac or the key's name, and why it asks again) and the chat that asks in `~/.claude/claudopus/boxes` and takes what you type in the panel from the keychain under that request's id, removing it at once, in every chat; only when no chat with a panel takes the request within 15 seconds (a `claude -p` run with no chat open on this Mac) does it ask in a macOS dialog (`osascript`) instead, and never over SSH; it saves the value in this Mac's keychain (`security`), and runs only the command it is handed, on this Mac or over SSH to the host named, as root with the system's own `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin` on a Mac), never the caller's. Each reads only its own keychain service (`claudopus-admin`, `claudopus-secret`), whatever its environment says. `bin/admin` runs a command as root only with a grant the hook sealed for that Mac and that exact command after your press, under two minutes old, and takes it once; with none it refuses, however it was reached, and only `"admin": "never"` sealed by Config runs without one. The seals are HMACs under a key in this Mac's keychain (`claudopus-admin-gate`), made with `openssl`, `security` and `perl`; whatever runs as you and reads the keychain could make one, as it could read a saved password. Claudopus saves no admin password, and no setting changes that: each command asks for it. On this Mac, at its screen, `bin/admin` hands the command to `osascript` (`do shell script ... with administrator privileges`), so macOS asks in its own box, which names the command; elsewhere (over SSH, on Linux, in a chat reached from another device) a box at the top of the panel of the chat that asked asks, sealed to a key that one run made and dropped after it. Claudopus removes a password an earlier version saved, and the `adminPassword` setting, as it loads. `workflows/rounds.js` is a workflow script the chat starts through the Workflow tool as `claudopus:rounds`. `onboard/` (a Python script and its instructions) loads old chats into the memory. It runs only when you press Index my old chats on the welcome a new install shows once, which asks the chat to run it as a background task.

## Files that will be held for a reviewer, and why they stay

- The hooks module itself: the panel, the cards and every behaviour above are this code.
- `bin/revive`: brings Claudopus back in a chat where Claude's engine switched it off. Each chat's Claudopus writes `~/.claude/claudopus/keep/<chat>.beat` every three seconds (the chat's process number, its copy's key in the settings, and the settings file it reads) and starts one `bin/revive` on the Mac, detached with `nohup` and `perl`'s `setsid` so it outlives the chat. When a beat is quiet 10 seconds while its process still runs, it sets that copy's own hidden option, `pluginConfigs.<key>.options.revived`, to the time in that settings file (`~/.claude/settings.json`, or the one under `CLAUDE_CONFIG_DIR`), with `osascript`'s JavaScript (`python3` on Linux), every other key as it was; Claude Code then loads Claudopus again in every chat, as an update does. It leaves a file it cannot carry whole (comments, numbers over 15 digits), a copy turned off in `enabledPlugins`, and a chat that has not come back after three tries, until that chat beats again. It ends once no chat has beaten for ten minutes. What it did is in `keep/revive.log`. A file `keep/<chat>.hold-test` holding a chat's process number makes that chat's Claudopus hold Claude's helper for ten seconds once, to show the switch-off and the return.
- `bin/release`: the only way a task puts changes on a repo's main, one at a time.
- `bin/admin` and `bin/secret`: the only way a task gets an admin command or a key without the value passing through a chat.
- `bin/pane-file`: puts a file from this Mac into a page's upload box in the Claude app's browser pane, where no file window opens. Claude starts it for the files it names; it serves them on `127.0.0.1` only, behind a random id made for that run, to pages that send the pane on to the site Claude names with one part of a file after the `#`; JavaScript Claude runs on that site stores the parts in the site's own browser storage, sets the file on the upload box and removes those parts. Parts of an upload left unfinished stay in that site's storage until Claude runs the clearing line it prints. It sends nothing over the network itself, and stops 10 minutes after its last part is asked for.
- `bin/notify` and `notifier/`: the notifications' own two apps, purple Claudopus and amber Claudopus Asks with its sound (made by `notifier/sound.py`), built from `notifier/main.swift` by `notifier/build.sh` and signed ad hoc; macOS takes a notification's icon from the app that sends it, and opens what a click names only for an app. `notifier/checksums.txt` holds the SHA-256 of every file of both apps and of what they are built from (`main.swift`, `icon.swift`, `sound.py`, `Info.plist` and Claudopus's icon), with the compiler and macOS SDK `build.sh` used (the first record was made after the build, from the committed apps, so it names only the SDK read from the program); `build.sh` writes it, and `notifier/check.sh`, run by the repo's CI and by every release, fails when a committed file differs from it or an app holds a file it does not name. To compare for yourself, on a Mac with Xcode or the Command Line Tools: copy the repo, run `sh mods/claudopus/notifier/build.sh` there, and compare its new `checksums.txt` with the committed one (`git diff mods/claudopus/notifier/checksums.txt`). The icons, the sound, both `Info.plist` and the signature's seal of the resources come out the same byte for byte; the program, `Contents/MacOS/Claudopus`, comes out the same only with the same compiler and SDK. The committed apps were built with macOS SDK 27.2: a rebuild with Xcode 27.1 (Swift 6.4, SDK 27.0) gives the same program twice in a row but not the committed one, so with another toolchain compare the rest and read the program's code, 125 lines of `main.swift`.
- `workflows/rounds.js`: the workflow, with one agent making and another checking, that the chat starts.
- `onboard/extract.py`: reads your past chats under `~/.claude/projects` into the memory; it runs only after you press Bring in old chats.
- `sounds/ready.wav`, `art/panel.png` and the icon: the chime, the README's picture and the listing icon.
